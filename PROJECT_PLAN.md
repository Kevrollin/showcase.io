# Showcase — Project Plan

> "Everything you sell or do, in one simple link."

Showcase is a lightweight digital storefront and portfolio builder for student
entrepreneurs, freelancers and small local businesses. The core journey is
**Create → Showcase → Share → Get enquiries** (enquiries happen on WhatsApp).

This document is the implementation plan. It was written before the build and is
kept in sync with the decisions that shaped the code.

---

## 1. Product architecture

```
             ┌──────────────────────────── Vercel ─────────────────────────────┐
 Browser ──▶ │  Static SPA (Vite build, /dist)        api/share-preview.ts      │
             │  - marketing site (public)             (crawler-only rewrite of  │
             │  - public storefront /s/:slug          /s/:slug[/:item] → HTML   │
             │  - auth + dashboard (lazy chunk)        with Open Graph tags)    │
             └───────────────┬───────────────────────────────┬─────────────────┘
                             │ anon key + user JWT           │ anon key only
                             ▼                               ▼
             ┌──────────────────────────── Supabase ───────────────────────────┐
             │ Auth (email+password)   PostgREST (RLS)   Storage (catalog-media)│
             │ Postgres: profiles, plans, businesses, categories,               │
             │           catalogue_items, catalogue_images  + RPC functions     │
             └──────────────────────────────────────────────────────────────────┘
```

* **No custom backend server.** All reads/writes go through Supabase with Row
  Level Security as the enforcement layer. The only server code is one Vercel
  Function that renders social-preview HTML for crawlers.
* **Two bundles worth of weight.** Public pages (landing, storefront, legal)
  never import `@supabase/supabase-js`; the storefront talks to two
  `SECURITY INVOKER` RPCs with a ~1 KB `fetch` wrapper. Auth/dashboard routes are
  lazy chunks that bring in supabase-js, forms and Radix primitives.
* **Layering.** `services/*` (Supabase calls, no React) → `features/*/hooks`
  (TanStack Query) → `features/*/components` (UI). Validation schemas live in
  `lib/validation`. Pure helpers (phone, slug, price, WhatsApp links, image
  compression) live in `lib/utils` and are unit tested.

## 3. Database model

```
auth.users 1─1 profiles ─┬─ plan_id ─▶ plans (limits: businesses, published, items, images)
                         │
                         └─1─* businesses ─┬─1─* categories
                                           ├─1─* catalogue_items ─1─* catalogue_images
                                           └─ (category deletion → items.category_id = NULL)
```

* `profiles(id → auth.users, full_name, plan_id)` — created by trigger on signup.
  `plan_id` is not client-writable (column privileges).
* `plans(id, max_businesses, max_published_businesses, max_items_per_business,
  max_images_per_item)` — the single source of truth for tier limits, enforced by
  triggers. Free: 1 business, 1 published storefront, 300 items, 8 images/item.
* `businesses` — identity, contact, appearance, `status` (`draft | published |
  unpublished`), `onboarding_step`, `onboarding_completed_at`, slug (lowercase,
  unique, reserved words blocked).
* `categories(business_id, name, sort_order)` — unique name per business.
* `catalogue_items(business_id, category_id?, item_type, title, slug, price,
  currency, price_mode, availability_status, is_featured, is_published, sort_order)`
  — slug unique per business, generated by trigger.
* `catalogue_images(business_id, item_id, storage_path, thumb_path, width, height,
  byte_size, alt_text, sort_order)` — `business_id` must match the item's
  business (trigger), first image by `sort_order` is the primary image.

RPCs: `is_slug_available`, `get_storefront`, `get_storefront_items`,
`get_storefront_item`, `reorder_items`, `reorder_categories`, `reorder_images`,
`delete_my_account`.

## 5. Security strategy

* RLS on every table; ownership derived from `auth.uid()`, never from client input
  (`owner_id` defaults to `auth.uid()` and a check policy pins it).
* Anonymous role gets `SELECT` on public columns only (column privileges) and
  only rows that belong to published businesses / published items.
* Storage bucket `catalog-media`: public read (unguessable UUID paths), writes
  restricted by policy to `"{auth.uid()}/{business_id owned by caller}/…"`,
  MIME allow-list (JPEG/PNG/WebP) and 2 MB limit at the bucket level.
* Plan limits enforced by triggers, not the UI.
* No service-role key anywhere in the repo or frontend env. Account deletion is a
  `SECURITY DEFINER` function that can only delete `auth.uid()`.
* User content rendered as text only (no `dangerouslySetInnerHTML`); the
  share-preview function HTML-escapes every interpolated value.

## 6. Testing strategy

* **Unit (Vitest):** phone normalisation, slugify, price formatting, WhatsApp
  links, URL/social normalisation, validation schemas, image sizing maths,
  share-preview HTML rendering + crawler handler.
* **Component (Vitest + RTL):** storefront rendering & filters, item cards,
  onboarding type step, auth form validation, protected-route redirect.
* **Database (Vitest + PGlite):** migrations applied to a real Postgres (WASM)
  with a Supabase shim (`auth.uid()`, roles, `storage` schema). Covers allowed and
  denied operations for anon / owner / other user, storage path policies, plan
  limits, slug rules. Mirrored as pgTAP in `supabase/tests` for `supabase test db`.
* **E2E (Playwright):** landing navigation + mobile menu, auth validation, route
  protection, storefront browsing/search/filter/item detail/WhatsApp links and
  not-found — run against the production build with the Supabase HTTP API stubbed.
  An opt-in suite runs the full signup → onboarding → publish journey against a
  real Supabase project (`E2E_SUPABASE_URL`).
